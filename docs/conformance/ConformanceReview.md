## Recovery semantics reviewed

`OperationJournal.create` must succeed before any operational content/tag/taxonomy mutation. It records operation identity, affected filenames/section IDs, prior/intended content fingerprints, prior/intended resource state, progress and errors. Initial backend boundary setup/preflight is a separate mandatory initialization activity. Individual JSON records are flushed before replacement; no power-loss durability or cross-store transaction claim follows.

`DiaryPersistence.content_change` writes content once and observes committed/not-written/uncertain state. Only confirmed intended content proceeds to metadata. An interrupted/failed write that happens to leave the complete intended bytes can be reported as partial and subsequently reconciled; unknown/truncated bytes require inspection. Multi-file completion is not atomic: a failed later write retains a record of earlier commits, and retry never completes the remaining file by replaying a content write.

Metadata reconciliation runs through closed adapter sessions and fresh readback. It checks rejected-tag lists and verifies deleted-resource absence, not just an empty association list. Checkpoints and planned in-flight states allow known partial progress to be retried. New foreign associations, changed content and ambiguous targets stop recovery without mutation. Interruption during a mutation retains its intent and reports the observed operation outcome with CLI status 130. A conflict is not adopted as a fresh checkpoint, so repeated retries cannot gradually authorize overwriting divergence.

Completed/resolved receipts remain in the journal. Retry of such an ID is a no-op even after later manual changes. A lost receipt acknowledgement is handled by inspecting the durable receipt; when it cannot be inspected, the possible completion record is retained rather than overwritten with a pending record. Explicit resolution records a reason without mutating either data store. All of these are sequential recovery guarantees, not isolation, automatic rollback or arbitrary crash repair.

The user commands are `recovery list [--all]`, `recovery show ID`, `recovery retry ID`, and `recovery resolve ID --reason TEXT [--yes]`. Mandatory HTFS preflight still applies. Their names/schema are implementation choices within the already approved policy.
